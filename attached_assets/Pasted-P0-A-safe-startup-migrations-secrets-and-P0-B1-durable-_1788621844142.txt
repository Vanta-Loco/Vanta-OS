P0-A safe startup/migrations/secrets and P0-B1 durable Member sessions are complete.
Implement ONLY durable named Admin authentication.
Do not begin media/object storage, Vault delivery changes, cookies/CSRF, rate limiting, observability, Creator work, or unrelated feature work.
Goal
Replace the current shared Admin password / global in-memory Admin token / MemoryStore dependency with durable, named Admin accounts and durable Admin sessions.
Preserve:
all existing Admin pages
Member Management
Creator certification
all existing Admin-protected APIs
Admin authentication must remain completely separate from Member authentication.
1. Inspect existing Admin auth first
Review:
server/admin-auth.ts
Admin login route
Admin middleware
Admin frontend login flow
current Admin token/header handling
current Express session usage
legacy user_sessions table discovered during P0-B1
Do not modify the existing Member member_sessions system.
2. Add named Admin identities
Add a forward-only migration for a table such as:
admin_users
Suggested fields:
id UUID
username
password_hash
display_name nullable
is_active
created_at
updated_at
last_login_at nullable
Admin usernames must be unique.
Do not use the normal Member users table for Admin identities.
Do not grant Admin privileges through Member roles during this stage.
3. Durable Admin sessions
Add:
admin_sessions
Suggested fields:
id UUID
admin_user_id
token_hash
created_at
expires_at
last_used_at
revoked_at
Generate a cryptographically random opaque token.
Store only a secure token hash in PostgreSQL.
Never store raw Admin bearer tokens.
Do not expose Admin session data through Member/Admin APIs.
4. Preserve the current Admin client contract where practical
Inspect the current Admin frontend/header contract.
If Admin currently uses a separate bearer/header token, preserve that API shape where reasonable so the Admin UI does not need a broad rewrite.
Only change the login UI as much as needed to support:
Admin username
Admin password
Do not mix Member X-User-Token authentication with Admin authentication.
5. Bootstrap first named Admin safely
We currently have a shared ADMIN_PASSWORD environment secret from the old system.
Do NOT automatically create an Admin account during normal application startup.
Add an explicit bootstrap/admin-creation command, for example:
npm run admin:bootstrap
or another clear explicit command.
It should:
run manually only
create the first named Admin safely
hash the password using a strong password-hashing method consistent with the project
refuse accidental duplicate creation
never print the password
Prefer reading bootstrap credentials from secure environment variables or a safe interactive mechanism.
Normal application startup must remain schema- and seed-neutral.
6. Retire shared-password runtime auth
After the first named Admin exists and the new login flow is verified:
normal Admin login must authenticate against admin_users
remove dependence on one shared global Admin password
remove dependence on one process-local global Admin token
remove Admin dependence on MemoryStore for authentication
Do not delete the legacy user_sessions table during this stage.
Preserve its existing rows untouched unless there is a proven safe reason to change them.
7. Production secret behavior
Once named Admin authentication is fully database-backed, reassess the P0-A requirement that normal production runtime requires:
ADMIN_PASSWORD
The long-term application runtime should not require a shared Admin password after bootstrap.
If ADMIN_PASSWORD is needed only for the explicit bootstrap command, move that requirement out of normal server startup validation.
Do not weaken validation for:
DATABASE_URL
SESSION_SECRET
VAULT_CODE
Do not expose secret values.
8. Admin middleware
Update the existing shared Admin middleware so every Admin-protected route validates:
presented Admin session token
token hash lookup
session not revoked
session not expired
associated admin_users.is_active = true
Existing Admin routes should continue using centralized middleware.
Do not add individual authentication checks route by route.
9. Login / logout
Admin login:
username + password
active Admin only
create durable Admin session
update last_login_at
Admin logout:
revoke only the presented Admin session
Application restart must not invalidate a valid Admin session.
Multiple application instances must be able to validate the same Admin session.
10. Security
no raw Admin tokens in DB
no tokens/passwords/hashes in logs
timing-safe credential verification where applicable
parameterized SQL
session expiry required
inactive Admin accounts rejected
Do not implement rate limiting yet; that is a later P0 stage.
11. Preserve existing authorization
Confirm these remain protected by Admin middleware:
Admin dashboard
Member Management
suspend/reactivate Member
Certified Creator management
existing Admin content controls
Member suspension must have no effect on Admin accounts because these are separate identity systems.
12. Migration
Add schema only through the versioned migration system from P0-A.
Do not put table creation into normal startup.
Suggested migration:
0003_durable_admin_auth
Do not alter member_sessions.
13. Cleanup
Add an explicit Admin-session cleanup mechanism or extend the existing maintenance approach cleanly.
Expired/revoked Admin sessions should be removable without introducing a background worker.
