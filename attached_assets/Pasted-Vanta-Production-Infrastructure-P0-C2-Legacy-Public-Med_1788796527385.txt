Vanta Production Infrastructure — P0-C2: Legacy Public Media Migration
Use Power Mode.
P0-C1 durable Vanta Media Storage is complete using Replit App Storage.
Implement ONLY migration of existing public legacy image media from local /uploads into the existing Vanta Media/App Storage architecture.
Do NOT migrate Vault audio or Release audio yet.
Do NOT remove local /uploads serving yet.
Do NOT delete legacy files.
This must be a copy-first, verify-first, rollback-safe migration.
Goal
Move existing public image references that currently depend on:
/uploads/...
into durable App Storage while preserving all existing Vanta content and frontend behavior.
At the end of this stage:
new images → App Storage
existing public images → App Storage
while legacy local files remain temporarily available as rollback copies.
Private/restricted audio remains untouched for P0-C3.
1. Inventory legacy media first
Before changing anything, inspect:
local uploads/
database fields containing /uploads/...
Transmission cover images
Transmission gallery images
other published image fields
any legacy profile/image references
Classify each discovered asset as:
public image
audio
unknown
orphaned/unreferenced
Do not assume every /uploads file is an image.
Produce an inventory count before migration.
2. Explicit exclusions
Do NOT migrate during P0-C2:
Vault source audio
Vault compressed audio
Release source audio
Release previews
private/unpublished audio
generated Room environment source assets
frontend-bundled application assets
arbitrary unknown files
Leave those unchanged.
If classification is uncertain, skip the asset and report it.
3. Backup before migration
Create and verify a fresh PostgreSQL backup before rewriting any database media reference.
Also record a manifest of legacy files involved in this migration containing at least:
local legacy path
byte size
SHA-256 checksum
database references
migration status
Do not delete the manifest after migration.
The temporary database backup should be clearly identified as temporary unless stored durably elsewhere.
4. Migration command
Implement an explicit maintenance command such as:
npm run media:migrate:legacy
Normal application startup must never automatically migrate media.
Prefer supporting:
--dry-run
and an explicit apply mode if practical.
A dry run should:
scan
classify
report
make no database or object-storage changes
5. Copy-first migration
For every eligible legacy public image:
Read the existing local file.
Verify it is a valid image.
Calculate SHA-256.
Store it through the existing media-storage.ts abstraction.
Create a media_assets record.
Verify the stored object exists.
Verify its byte count/checksum or equivalent integrity.
Only then update database references.
Never update the database reference before durable storage verification succeeds.
6. Preserve existing image appearance
Do not unnecessarily recompress or visually modify legacy images during migration.
If a legacy image is already the processed/normalized asset currently shown by Vanta, prefer transferring those exact existing bytes to App Storage.
Migration should change storage location, not creative appearance.
Do not rerun Sharp merely because the image is being migrated unless validation requires decoding.
7. Stable Vanta URLs
Update migrated database references to use the stable Vanta Media route:
/media/assets/:id
rather than exposing raw provider URLs.
Continue using the existing provider abstraction.
Do not make database records depend directly on Replit App Storage URL structure.
8. Database-reference safety
Locate every actual database reference before updating it.
Examples may include:
Transmission cover image
Transmission gallery entries
other public image columns discovered during inventory
Use parameterized updates.
Preserve:
post IDs
gallery order
image formatting/layout metadata
captions
content ownership
publication state
Do not alter unrelated post/content fields.
9. Duplicate files
If the same physical legacy image/checksum is referenced multiple times, avoid unnecessarily storing duplicate object copies where the existing media architecture can safely share one Media Asset.
However, do not perform aggressive deduplication if it could alter ownership or deletion semantics.
Correctness and reversibility are more important than storage optimization.
10. Orphan files
Do not automatically delete or migrate unreferenced legacy files.
Report:
referenced legacy images
migrated images
skipped images
orphan images
audio files
unknown files
Orphan cleanup is a later maintenance stage.
11. Failure behavior
Migration must be resumable/idempotent where practical.
If one asset fails:
do not corrupt its current database reference
do not delete its local file
record/report the failure
Avoid leaving database records pointing to missing App Storage objects.
If a media_assets record was created but its reference update fails, report/reconcile it safely rather than deleting aggressively.
12. Legacy fallback
Keep:
/uploads
serving enabled after migration.
Do not delete local legacy images.
This creates a rollback window.
After successful migration, normal database references should prefer /media/assets/:id, but old local files remain physically available.
Removal of local serving happens only after C3 and final media verification.
13. Existing P0-C1 uploads
Do not remigrate assets that are already represented correctly in:
media_assets
or already use:
/media/assets/:id
Preserve the intentional P0-C1 verification asset.
Do not implement garbage collection.
14. Security
Do not trust file extension alone.
Validate legacy assets as actual images before migration.
Unknown/executable/corrupt files should be skipped and reported.
Do not expose:
App Storage credentials
raw storage internals
Admin tokens
Member tokens
15. No schema-in-startup regression
If schema changes are genuinely necessary, use the existing versioned migration system.
Do not restore schema initialization to application startup.
Prefer using the existing media_assets schema without unnecessary database changes.
16. Preserve
Do not modify:
Member auth/sessions
Admin auth/sessions
Member suspension
Passport
XP/achievements
Creator systems
Rooms
Marketplace
Vanta Play
Vault authorization/delivery
Release audio behavior
World
navigation
Photos-library frontend behavior
Verification
Run:
migration dry run
migration apply
npm run check
npm run build
git diff --check
Then verify:
Record pre-migration counts and manifest.
Existing Transmission images load before migration.
Migrate eligible public legacy images.
Confirm corresponding objects exist in App Storage.
Confirm media_assets records exist.
Confirm checksums/integrity match.
Confirm database URLs now use /media/assets/:id.
Open existing Transmission posts.
Confirm cover images look unchanged.
Confirm galleries preserve order and image-layout behavior.
Restart the application.
Confirm all migrated media still loads.
Confirm a newly uploaded P0-C1 image still works.
Confirm original local files still exist.
Confirm legacy audio URLs and database references were untouched.
Run migration again and confirm it safely skips already migrated assets.
Return a final migration report containing:
legacy files scanned
eligible public images
successfully migrated
skipped
failed
orphaned
audio deliberately excluded
unknown files
database references updated
Stop after P0-C2.
Do not begin Vault/Release audio migration.
