P0-A safe startup/migrations/secrets, P0-B1 durable Member sessions, and P0-B2 durable named Admin authentication are complete.
Implement ONLY the durable media-storage foundation and migration of new media writes.
Do NOT migrate existing legacy /uploads files yet.
Do NOT change Vault authorization/delivery yet.
Do NOT delete local files.
Preserve all existing Vanta functionality.
Goal
Establish one shared Vanta Media layer backed by durable object storage so future media does not depend on the local Replit filesystem.
New compatible uploads should begin writing to durable storage.
Existing legacy /uploads/... references must continue working unchanged during this stage.
1. Inspect current media architecture first
Audit all code paths involving:
/uploads
/api/upload
Multer
Sharp
Transmission cover images
Transmission gallery images
Vault audio
Release audio
compressed/preview audio
any file delete/update logic
generated Room environment assets
Creator external media URLs
Identify every database field containing local /uploads/... URLs or paths.
Do not modify them yet.
2. Object-storage provider
Inspect what durable object-storage capability is available in this Replit project/environment.
Prefer the platform-supported Replit object-storage integration if it is available and appropriate.
Otherwise use the smallest production-suitable object-storage integration supported by the environment.
Do not invent credentials or hardcode provider secrets.
Required provider configuration must come from environment/deployment secrets.
If no supported object-storage service can safely be configured from this workspace, stop before implementation and report exactly what account/configuration step I must perform.
3. Storage abstraction
Add a focused server-side media/storage module rather than scattering provider calls across routes.
It should provide operations conceptually equivalent to:
store object
retrieve/public URL metadata
delete object
inspect object
generate private access later
Keep provider-specific implementation behind this layer.
Do not redesign the entire server.
4. Media database records
Add a forward-only migration for a table such as:
media_assets
Suggested fields:
id UUID
storage_key
owner_user_id nullable
namespace
purpose
original_filename
mime_type
byte_size
width nullable
height nullable
duration_seconds nullable
visibility
processing_status

created_at
updated_at
deleted_at nullable
Visibility should support future concepts such as:
public
unlisted
private
Do not modify existing app tables to require media_assets.id during this stage.
Existing URL columns should remain compatible.
5. Media namespaces
Design the media layer so the same system can eventually support:
transmission
creator
rooms
vault
releases
profiles
P0-C1 does NOT need to activate all of them.
Do not create separate upload systems for every Vanta app.
6. New Admin image uploads
Migrate the existing generic Admin image upload path to durable storage.
Preserve its frontend/API behavior as much as possible so Transmission does not need a broad frontend rewrite.
Existing working Photos-library handling must remain intact:
browser file materialization
sequential gallery uploads
Sharp normalization
auto-rotation
WebP conversion
metadata stripping
transparency support
The resulting stored media should live in object storage rather than local /uploads.
Return a stable usable media URL/reference compatible with the existing Transmission flow.
7. Do not migrate old media yet
Existing records pointing to:
/uploads/...
must remain functional.
Do not:
rewrite legacy database URLs
move existing files
delete existing files
remove Express /uploads serving
Legacy migration is P0-C2.
During this stage Vanta may temporarily support:
legacy local reads + durable new writes
That is intentional.
8. Upload hardening
Improve validation for the new durable upload path without breaking valid Transmission uploads.
Do not trust only the browser MIME header.
For image uploads:
verify actual image decoding/content with Sharp
enforce a clear maximum byte size
enforce sensible maximum pixel dimensions
reject corrupt/unsupported content
use generated storage keys rather than user-controlled filesystem names
Do not accept arbitrary executable content.
Do not enable Member uploads yet.
The current Admin uploader must remain Admin-protected.
9. Checksums
Where practical, calculate a cryptographic checksum such as SHA-256 for newly stored assets.
Record it in media_assets.
This will be used during the legacy migration to verify byte-for-byte transfer.
10. URL/storage-key separation
Avoid making application logic depend permanently on one provider’s raw URL structure.
Persist:
durable storage key
media metadata
while returning a usable URL/reference through the storage layer.
Do not prematurely rewrite every existing frontend to use Media IDs.
Compatibility first.
11. Delete behavior
Inspect existing image removal/update behavior.
Avoid deleting underlying object-storage assets merely because an editor temporarily removes a reference unless the current semantics clearly require permanent deletion.
Prefer safe soft/orphan handling for now.
Do not build a full garbage collector yet.
12. Vault and audio
Do NOT migrate Vault or Release audio during P0-C1.
Do NOT make Vault public object storage.
Do NOT alter /uploads audio serving yet.
The storage abstraction should be capable of private media later, but actual Vault migration/protection belongs to P0-C3.
13. Creator uploads
Do not expose the new media service directly to Members yet.
Creator Work should continue supporting its existing external URLs.
Creator avatars, banners and Work uploads come after the media foundation is proven.
14. Generated application assets
Fashion/Music Room rendered environment images that are bundled as application source assets do NOT need to be moved to object storage.
Leave bundled static application assets alone.
15. Production configuration
Add clear validation for the object-storage configuration required in production.
Do not log:
storage secrets
signed credentials
raw authorization headers
Development may use a clearly identified development configuration if necessary.
Do not silently fall back to ephemeral local disk in production.
16. Migration discipline
Add schema only through the versioned migration system.
Suggested migration:
0004_media_assets_foundation
Do not put schema initialization back into normal startup.
