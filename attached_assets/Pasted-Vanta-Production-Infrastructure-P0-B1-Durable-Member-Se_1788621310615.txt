Vanta Production Infrastructure — P0-B1: Durable Member Sessions
Use Power Mode.
P0-A safe startup/migrations/secrets is complete.
Implement ONLY durable Member authentication sessions.
Do not begin Admin-auth migration, object storage, Vault media migration, rate limiting, CSRF, or unrelated infrastructure yet.
Goal
Replace the current process-memory Member token Map with durable database-backed sessions while preserving the existing:
X-User-Token
API contract and current frontend behavior.
Existing Member identities, passwords, UUIDs, Passport, suspension semantics, Creator systems, Rooms, Marketplace, Play and all other Vanta applications must remain intact.
1. Inspect existing Member auth
Review:
server/user-auth.ts
registration/login/logout routes
requireUser
getRequestUser
client/src/hooks/use-user.ts
anywhere X-User-Token is consumed
Do not rewrite frontend authentication unless required.
2. Add durable Member sessions
Add an additive session table such as:
user_sessions
Suggested fields:
id UUID
user_id
token_hash
created_at
expires_at
last_used_at
revoked_at nullable
Optionally include safe device/session metadata only if already available cleanly.
Never store the raw bearer token in the database.
Generate a cryptographically random opaque token for the browser and store only a secure hash of it.
Preserve the existing browser-facing:
X-User-Token: <opaque token>
contract.
3. Session expiry
Add an explicit expiry policy.
Choose a sensible Alpha default and centralize it in configuration.
Do not create permanent non-expiring sessions.
Expired or revoked sessions must be rejected.
4. Registration / login
On successful registration or login:
verify the Member is active
generate a new opaque session token
store its hash durably
return the raw token exactly once to the existing frontend
Preserve the current response shape where practical so existing clients continue working.
Suspended Members must continue receiving:
HTTP 403
ACCOUNT_SUSPENDED
and must not receive a new session.
5. requireUser
Replace process-memory token lookup with durable session lookup.
For every protected request:
Read X-User-Token
Hash/lookup the session
Verify:
session exists
not revoked
not expired
Load current Member state
Check current users.account_status
If active, continue
If suspended, return existing ACCOUNT_SUSPENDED
Suspension must remain immediately effective even for sessions issued before suspension.
6. Logout
Existing Member logout should revoke only the presented durable session.
Do not delete the Member account.
Do not rely on deleting data from an in-memory Map.
7. Restart / autoscale requirement
This is the primary acceptance criterion:
A Member logged in before an application restart must remain authenticated after restart as long as:
the durable session has not expired
it has not been revoked
the Member remains active
Multiple application instances must be able to validate the same session through the shared database.
Remove Member authentication dependence on process-local state.
8. Legacy development tokens
Inspect existing in-memory tokens.
Do not attempt to persist raw currently issued legacy tokens.
A one-time re-login for currently logged-in development users is acceptable when this migration is first deployed.
After migration, new sessions must be durable.
Do not keep insecure legacy token fallback enabled in production.
9. Security
Store only token hashes.
Use timing-safe practices where applicable.
Do not log raw session tokens.
Do not expose sessions through Admin Member APIs.
Do not expose session hashes.
Parameterize SQL.
Add appropriate indexes for token lookup and user/session cleanup.
Do not put password hashes or session data into general logs.
10. Session cleanup
Provide an explicit cleanup mechanism for expired/revoked sessions.
This may be:
explicit maintenance command
bounded cleanup during session creation
Do not introduce a background queue system during this stage.
11. Preserve all existing Vanta systems
Do not change:
users IDs
password hashes
Passport
XP / achievements
suspension semantics
Creator Profiles
Certified Creators
Creator Work
Rooms
Marketplace
Play
Transmission
Vault
Releases
World
Admin authentication
navigation
Do not migrate Member auth to HttpOnly cookies yet.
That is a later browser-security phase.
12. Migration
Add the session table through the versioned migration system created in P0-A.
Do not put schema creation back into normal application startup.
Application startup must remain schema-neutral.
Verification
Run:
npm run db:migrate
npm run check
npm run build
git diff --check
Then verify:
Member logs in successfully.
Protected Vanta action works.
Restart the application.
The same Member token still works without logging in again.
Logout revokes the session.
Revoked token no longer works.
Suspended Member receives 403 ACCOUNT_SUSPENDED.
Reactivating the Member restores access if the session remains valid.
Expired session is rejected.
Session tokens/hashes do not appear in Admin Member APIs or logs.
Stop after P0-B1.
Do not begin Admin session migration or media storage.
